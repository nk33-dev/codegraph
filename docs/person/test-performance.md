# 测试性能

## 本地实现

本轮基于已发布的 `4477e92`，改动只保留在本地，尚未推送或发布。

- 调用 Git 查询 HEAD、变化列表或可见文件前，以文件系统检查项目及祖先的 `.git`。明确不在仓库中的目录直接使用已有非 Git 路径，避免重复启动必然失败的子进程。判定不缓存，后续 `git init` 立即生效；worktree 指针、bare 仓库、环境指定仓库及不可确认的文件系统状态继续交给 Git 判定。
- 每次完整索引、指定文件索引和同步任务用独立的异步上下文复用 `core.excludesFile` 路径。同一任务、同一目录和 Git 配置环境只查询一次；下一次任务重新读取，ignore 文件内容仍在每次构造过滤器时读取。未配置结果可以复用，命令失败继续重试。Git 仓库的 HEAD、status、提交差异和文件清单仍实时查询。
- `check:quick` 与 `test:focused` 只执行 engine/ui。engine 与 perf 共享的测试文件在普通检查只运行一次；`test:perf` 保持串行和严格计时断言。
- 受影响测试选择每个测试文件只读取、解析一次；直接导入和领域规则保持不变。共享入口变化可能仍会选中大量测试，不以缩小覆盖范围制造加速。
- Windows CI 使用三个独立 runner，分别执行 Vitest `--shard=1/3`、`2/3`、`3/3`，每台两个文件 worker。Ubuntu/macOS 各使用一台 runner、四个 worker。每台按原流程安装和构建，所有分片通过才算 CI 通过；分片降低等待时间，也增加安装、构建的总资源消耗。

## Windows 本机测量

Node v24.16.0，同一天、同机器、同源码样本；测量脚本在临时目录，不进入发布包。

仅一个 TypeScript 文件、非 Git 临时项目，连续三次建索引后做无变更同步：

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| Git 调用数 | 17 | 2 |
| Git 累计耗时 | 1,051～1,087 ms | 126～139 ms |
| 建索引 | 684～775 ms | 299～383 ms |
| 无变更同步 | 626～682 ms | 152～186 ms |
| 建索引＋同步中位数 | 1,365 ms | 453 ms |

Git 调用的剩余成本是每次任务一次的全局 ignore 配置读取；此样本中每个 Git 子进程约耗时 60～90 ms，正文提取只有毫秒级成本。

真实 Git 仓库的同样一个文件样本，与上一轮本地提交 `5513cf8` 对照，三次测量的调用数从 33 降到 27，Git 累计耗时从 2,088～2,286 ms 降到 1,756～1,915 ms，建索引＋同步中位数从 2,646 ms 降到 2,226 ms。真实仓库仍需查询工作区状态与提交信息，因此收益小于非 Git 临时项目。上述数字只覆盖小样本。

七个变更文件的测试选择从约 562 ms 降到 173 ms，优化前后均选中 277 个文件，逐行结果相同。这是单次测量，不作为严格延迟门禁。

## 验证与范围

新增回归覆盖任务内复用、未配置结果、命令失败重试、并发任务隔离、目录/环境变化、下次任务的配置变化及 ignore 文件内容变化。实际非 Git 项目索引、同步各只读取一次配置。提交/restore/指定文件索引/失败回退与 ignore 配置回归也已通过；运行证据见[开发验证记录](test-repairs.md)。

使用本机安装的 Vitest 2.1.9 实际测试发现与默认 sequencer 的分片逻辑核对：engine/ui 共 381 个文件，三片各 127 个，交集为空、并集完整。此检查只发现和分配文件，没有运行全量测试。`vitest list --shard` 不执行分片，不能用它验证覆盖。

优化尚未推送，GitHub 上的三台 Windows runner 并行耗时、排队时间和三平台完整结果待下一次 CI 测量。Windows 原发行耗时及先前同步/解析对照保留在[开发验证记录](test-repairs.md)。
