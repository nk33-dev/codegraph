# AI 优先能力与资源治理开发计划

状态：阶段一至阶段五已实现并完成本地验证；阶段六已形成提交与个人预发布交付，跨平台工作流实跑、真实仓库评测和能耗测量待完成

适用分支：`personal`

> 阶段一的实现契约、代码归属和验证结果见[资源档位与自动回收](../person/resource-governance.md)。
> 阶段三的覆盖契约与验证边界见[高价值动态分派补全](../person/dynamic-dispatch.md)。

## 1. 背景与定位

CodeGraph 的主要用户是 AI 编程代理，不是把图查询结果直接交给人类浏览的普通代码搜索产品。功能价值按以下顺序判断：

1. AI 是否会通过现有入口自然使用它；
2. 是否减少后续 Read、Grep 和重复工具调用；
3. 是否减少错误关系、过度推断和无依据修改；
4. 是否降低上下文体积、查询延迟和写操作风险；
5. 是否能在多窗口、子 Agent 和电池供电场景下保持可控资源占用。

因此，本计划不以增加 MCP 工具数量为目标。运行时能力优先并入现有 `codegraph_explore` 和 `codegraph_edit`，CLI、状态页和评测命令主要服务人类操作者与维护者。

### 1.1 当前已有基础

- `codegraph_explore` 已是主要读取入口，能够返回源码、调用关系、动态边界、影响范围和关联测试；
- `codegraph_edit` 已支持默认预览、`previewHash`、陈旧文件拒绝和落盘后索引刷新；
- Graph/LSP 已有统一查询、自动路由、结果合并和不可用回退；
- LSP 按语言和项目懒启动，同一项目的多个客户端共享同一 `LspManager`；
- MCP 已有每项目共享 daemon、文件 watcher、增量同步和查询 worker 池；
- 已有动态分派 provenance、边界候选、实现者计数和跨轮源码去重；
- 当前 LSP 诊断是按需请求，不持续轮询；文件 watcher 的保存事件主要触发 Graph 增量索引，不会直接启动 LSP。

### 1.2 当前主要问题

#### AI 答案质量

- 关系证据、置信度、启发式来源和断链原因尚未形成统一输出契约；
- 查询接口或抽象方法时，实现者和运行时候选没有稳定地随答案自动展开；
- 动态分派覆盖仍有长尾，任一关键跳缺失都会迫使 AI 回到 Read/Grep；
- 改动影响、关联测试和 Git 变化已经分别存在，但尚未组合成 AI 可直接消费的改动上下文；
- 增加解释信息可能反过来造成输出膨胀，需要独立预算。

#### 写操作安全

- 跨文件编辑没有事务保证，后续文件写入失败时，前面已写入的文件会保留；
- 缺少稳定操作 ID 和完整恢复清单；
- 文件移动、创建和删除后的 LSP 文档通知仍不完整；
- 更复杂的签名修改、移动符号和 import 更新尚未形成统一计划器。

#### 多窗口和子 Agent 资源治理

- 查询池硬上限为 16；在当前 16 逻辑线程机器上，默认容量为 15；
- 查询池只预热 1 个 worker，但并发请求会扩容，扩容后不会自动缩容，直到 daemon 销毁；
- 同一项目的窗口和子 Agent 共享 daemon、查询池和 LSP，但不同项目或 worktree 会各自创建资源；
- LSP 限制目前是每项目局部行为，没有跨项目的全局数量和内存预算；
- 还没有 `battery`、`balanced`、`performance` 资源档位；
- 语言服务器可能在启动后自行分析工作区，这部分不能仅靠 CodeGraph 的请求调度完全控制；
- 深度分支对比若直接维护双份完整索引，会放大 CPU、磁盘和耗电成本。

#### 交付与验证

- 个人功能仍处于本地开发状态，计划实施前需要先形成可审查提交链；
- 缺少面向 push/PR 的常规跨平台构建、测试和性能门禁；
- 当前检索收益数字主要是历史上游测量，个人版需要重新建立基线；
- 性能断言会受全量并发测试负载影响，应与普通正确性测试分离。

## 2. 目标与非目标

### 2.1 总体目标

- AI 在小型仓库通常通过 1 次 `explore` 得到足够答案，中型仓库控制在 2 次左右，大型仓库控制在 3～5 次；
- 返回的关键路径均能说明静态确认、LSP 确认、双方印证、启发式推导或未连接边界；
- 不为提高召回率而静默制造错误边；
- AI 审查改动时能够直接看到改动符号、影响范围、入口和关联测试；
- AI 写操作达到可预览、幂等、可恢复，跨文件写入不留下不明状态；
- 单个用户同时运行多个窗口和子 Agent 时，资源按需求扩展并能自动回收；
- 电池模式下，不因后台分析长期占用 CPU，也不默认同时保留多套重型 LSP；
- 所有新增图推导由 `src/graph/` 或既有 resolution 层统一计算，CLI、MCP 和 UI 不各自实现一套。

### 2.2 非目标

- 不增加通用聊天 UI；
- 不默认引入云端服务、向量数据库或远程 embedding；
- 不自动安装语言服务器；
- 不承诺静态还原所有反射、宏、代码生成和运行时注入；
- 不用大量单用途 MCP 工具替代现有 `explore`；
- 不在电池模式后台自动运行全量索引、双分支索引或 Agent A/B 评测；
- 不为了缩短文件而一次性机械拆分所有上游大文件。

## 3. 目标架构

```text
AI 窗口 / 子 Agent
        │
        ├─ MCP proxy ───────────────┐
        │                           │
        ▼                           ▼
每项目共享 daemon             全局资源注册表
        │                    （profile、LSP lease）
        ├─ ToolHandler
        │    ├─ codegraph_explore
        │    └─ codegraph_edit
        │
        ├─ QueryPool ── Graph/SQLite 只读查询
        │
        ├─ CodeGraph 公共接口
        │    ├─ Graph 推导与证据模型
        │    ├─ 改动上下文与影响分析
        │    └─ 编辑计划与索引同步
        │
        ├─ LspManager ── 按需语言服务器
        │
        └─ FileWatcher ── 防抖后的增量索引
```

### 3.1 设计原则

1. **现有入口优先**：新增能力默认由 `codegraph_explore` 自动呈现，写能力进入 `codegraph_edit`。
2. **按需付费**：查询没有涉及 LSP、Git 改动或特定框架时，不运行对应逻辑。
3. **证据先于覆盖**：新增动态边之前先建立统一 provenance 和置信度输出。
4. **共享推导**：证据、实现者、改动影响和关联测试在 Graph 层计算，CLI/MCP/UI 只做适配和渲染。
5. **有界输出**：候选数、解释条目、源码字符数、查询时间和缓存空间都有上限。
6. **成功形状降级**：预期内的不支持、资源繁忙和未连接边界返回可行动说明，不轻易让 AI 放弃工具。
7. **活跃任务优先**：资源回收不终止正在执行的查询、索引或编辑。
8. **配置可见**：实际 profile、worker 数、LSP 数量和回收原因能从 status/日志确认。

## 4. 资源档位

第一版采用显式配置，不依赖不稳定的跨平台电池检测。建议新增 `CODEGRAPH_RESOURCE_PROFILE=battery|balanced|performance`，再评估是否增加用户级配置文件。现有精细环境变量继续保留并覆盖 profile 默认值。

| 项目 | battery | balanced | performance |
| --- | ---: | ---: | ---: |
| 查询 worker 初始值 | 1 | 1 | 2 |
| 查询 worker 最大值 | 2 | 4 | 8 |
| 查询 worker 空闲缩容 | 30～60 秒缩到 1 | 120 秒缩到 1 | 300 秒缩到 2 |
| 全量解析 worker 最大值 | 2 | 4～6 | 8 |
| 每项目 LSP 软目标 | 1 | 2 | 3 |
| 全局 LSP 上限 | 2 | 3 | 6 |
| LSP 空闲退出 | 90 秒 | 300 秒 | 600 秒 |
| 每项目会话缓存 | 64MB | 128MB | 256MB |
| 深度双索引 | 仅显式请求 | 按需临时创建 | 可预热 |

“battery 只保留一个 LSP”是软目标，不是每次语言切换都立即杀进程：

- 一个 LSP 可以服务同一语言家族的全部文件、窗口和子 Agent；
- 不关闭有活跃请求的 LSP；
- 默认保留最近使用的一个语言家族；
- TypeScript/Python 等语言短时间交替时可临时保留两个，避免反复启动更耗电；
- 超过全局上限时按最久未使用且无活跃请求的顺序退出；
- Graph 始终可用，能够诚实回退的查询不必为了精度偏好强制启动 LSP。

跨项目全局上限需要进程间协调。优先评估在用户级 CodeGraph 目录维护带 PID、启动身份、心跳和租约的锁保护注册表；不得只凭 PID 判断存活，也不得引入另一个永久常驻的中央服务，除非文件租约方案在 Windows/POSIX 上无法可靠工作。

## 5. 分阶段实施

### 阶段一：基线、资源档位和自动回收

目标：先让后续功能的 CPU、内存、磁盘和耗电增长可测、可限制、可回退。

实现内容：

- 记录查询队列长度、live/idle worker、单次查询耗时、缓存命中和 LSP 生命周期；
- 为 `QueryPool` 增加空闲时间与自动缩容，始终保留 profile 的最小 worker；
- 将当前按核心数推导的默认最大值改为 profile 上限，保留显式覆盖和硬上限 16；
- 增加每项目 LSP 软上限，随后实现跨 daemon 的全局 LSP lease；
- 增加资源 profile 解析、状态输出和启动日志；
- 给全量索引、增量索引、LSP 启动和查询分别记录基线；
- 将性能测试单独串行运行，普通全量测试不再用机器负载决定 100ms 断言结果；
- 建立 Windows/Ubuntu 的 build/test 门禁，真实 LSP、原生内核和能耗测量放夜间或手动任务。

主要入口：

- `src/mcp/query-pool.ts`
- `src/mcp/engine.ts`
- `src/mcp/daemon.ts`
- `src/lsp/manager.ts`
- `src/lsp/config.ts`
- `src/index.ts`
- `src/sync/watcher.ts`

验收标准：

- 当前机器单个 AI 串行查询时只保留 1 个查询 worker；
- 8 个并发只读调用完成后，balanced 模式在 2 分钟内缩回 1 个；
- 缩容不丢请求、不关闭活跃 worker、不破坏每 worker 独立 WAL 读取连接；
- 同一项目多个客户端仍只启动一套 LSP；
- battery 模式不会同时长期保留超过全局预算的 LSP；
- `status` 不启动 LSP，并能显示 profile 和实际资源状态；
- 所有资源治理均有关闭或回退开关。

预计综合评分：`8.2 -> 8.5`。

### 阶段二：统一证据、置信度和实现者展开

目标：让 AI 知道结论来自哪里、哪些部分不确定、何处需要保守回答。

实现内容：

- 建立内部统一证据模型，至少区分：`static`、`lsp`、`corroborated`、`heuristic`、`boundary`；
- 为关键路径输出定义位置、调用位置、注册位置和 `synthesizedBy`；
- 统一断链原因：未索引、无语法边、动态键、候选歧义、语言边界、LSP 不可用；
- 查询接口、trait 或抽象方法时，自动展开实现者和运行时候选；
- 实现者和边界候选均设数量、字符和时间预算；
- 复用现有 `findDynamicBoundaries`、`countImplementers` 和 provenance，不重复扫描；
- 将证据纳入跨轮去重，第二次调用只补充新证据和缺失源码；
- 文本输出保持适合模型阅读，同时在 structured content 中保留稳定字段。

建议内部契约：

```typescript
interface FlowEvidence {
  confidence: 'confirmed' | 'corroborated' | 'heuristic' | 'unknown';
  source: 'syntax' | 'graph' | 'lsp' | 'synthesizer' | 'boundary';
  location: { filePath: string; line: number } | null;
  detail: string;
}
```

验收标准：

- 每条启发式路径明确标注，不与静态确认路径混淆；
- 未连接时说明具体断点，不把候选描述成真实调用；
- 接口查询不需要 AI 再寻找独立 implementations 工具；
- 普通已连接路径的输出字符增长不超过 15%；
- 查询 p95 增长不超过 10%，超预算时优先裁剪解释而不是源码主干；
- 现有 `explore` 工具名称和基本输入保持兼容。

预计综合评分：`8.5 -> 8.7`，AI 使用价值约 `8.5 -> 9.0`。

### 阶段三：高价值动态分派端到端补全

目标：减少“图已返回大部分内容，但缺一跳迫使 AI 重读文件”的情况。

优先范围：

1. interface/trait/override 与依赖注入；
2. 事件总线和消息队列；
3. RPC/gRPC 与 handler 注册；
4. ORM、repository 和配置绑定；
5. 状态管理、路由和插件注册；
6. 只有运行时键才能决定的分派继续作为 boundary，不制造错误边。

实施要求：

- 按“分派形状”复用 resolver/synthesizer，不为每个框架复制整套实现；
- 只有检测到对应语言和框架时才运行规则；
- 每个新规则必须包含正例、歧义反例、跨语言反例和无框架控制项目；
- 新边继续携带 provenance、注册位置和 fan-out 上限；
- 每个语言×框架在小、中、大真实仓库上验证完整路径、错误边和 Agent A/B；
- 不完整的半条桥接不得作为完成状态。

验收标准：

- 选定 canonical flow 可以在规定 `explore` 次数内端到端连接；
- 真实仓库评测中 Read/Grep 回退明显下降；
- 节点数无异常增长，启发式边能够抽样解释；
- 全量索引时间相对阶段一基线增长不超过 30%；
- 数据库体积相对当前同仓库基线增长不超过 20%；
- 不涉及对应框架的项目额外成本接近零。

预计综合评分：`8.7 -> 8.95`，功能性约达到 `9.2`。

### 阶段四：AI 改动上下文和语义差异

状态：已实现并完成本地验证。实现契约、可信边界和验证范围见[AI 改动上下文与语义差异](../person/change-context.md)。

目标：让 AI 审查或修改代码时，不必自行拼接 Git diff、调用者、影响范围和测试。

实现内容：

- 从 Git changed files、changed ranges 和当前索引定位改动符号；
- 当 `explore` 查询明确涉及 review/change/impact，或返回文件与改动重叠时，附加改动上下文；
- 返回新增、修改、删除符号及调用边、继承边、路由边变化；
- 复用 `change-impact.ts` 输出受影响入口、传播距离和关联测试；
- 标出没有关联测试的高扇出改动，但不把“没有图边”表述为“肯定没有影响”；
- 普通改动分析只使用当前索引、Git diff 和局部邻域；
- 深度基准分支图只在显式请求时创建临时索引，使用独立目录，完成后清理；
- 不要求 AI 发现新的 MCP 工具；可为人类 CLI 提供独立命令，但底层必须复用 Graph 实现。

验收标准：

- AI 能在一次 `explore` 中获得改动符号、影响入口和关联测试；
- 没有明确改动意图且结果与改动无关时，不增加 Git 扫描和输出噪声；
- 普通局部分析不复制完整数据库；
- 深度双索引中断后可清理，不能覆盖当前项目索引；
- 分支切换、重命名、删除和未跟踪文件均有行为测试。

预计综合评分：`8.95 -> 9.1`。

### 阶段五：幂等、事务式结构化编辑

目标：让 AI 可以安全执行跨文件修改，并在失败后得到确定状态。

实现内容：

- 为每次 apply 增加稳定操作 ID 和结果记录，防止代理断线后重复应用；
- 将所有目标文件先验证并写入同文件系统暂存区，再进入提交阶段；
- 保留原文件指纹、备份位置、已提交文件和恢复状态；
- 提交失败时回滚已经替换的文件；若回滚也失败，返回逐文件确定状态和恢复清单；
- 保留 `previewHash`，操作 ID 不能替代内容一致性校验；
- 文件创建、删除、移动后向 LSP 发送支持的文档/工作区通知，无法通知时明确关闭旧文档；
- 在事务基础稳定后，再扩展签名修改、移动符号和 import 更新；
- 写操作仍在主线程或专用串行写通道执行，不进入只读查询池。

验收标准：

- 同一操作 ID 重试不会重复写入；
- 第二个文件失败时，第一个文件被恢复，或结果明确报告无法恢复的实际状态；
- 进程在暂存、部分提交和索引刷新阶段被终止后，下次启动能够检测并恢复；
- Windows 文件占用、CRLF、符号链接、跨卷移动和权限错误有契约测试；
- 写入完成后语法、索引和下一次查询保持一致；
- 默认仍只预览，AI 未明确 apply 时不写磁盘。

预计综合评分：`9.1 -> 9.2`，稳定性约达到 `9.3`。

### 阶段六：生产硬化、个人版评测和发布准备

目标：把前五阶段从可运行功能变成可持续维护和发布的个人版能力。

实现内容：

- 将个人改动按资源治理、证据契约、动态覆盖、改动上下文、编辑事务拆成可审查提交；
- 补 Windows、Linux、macOS 的核心构建和测试矩阵；
- 对真实 LSP、原生 kernel、daemon 恢复和长时间运行设置夜间测试；
- 在个人版真实构建上重新运行小、中、大仓库 Agent A/B；
- 记录 duration、Read、Grep、工具调用数、输出利用率、错误边、索引时间、内存和数据库大小；

## 6. 性能、内存与耗电预算

以下功率是相对于不运行 CodeGraph 的增量估算，必须在目标机器上实测后替换。当前参考机器为 Ryzen 7 6800H、8 核 16 线程、32GB 内存；当前项目约 892 个索引文件，数据库约 86MB，空闲 daemon 私有内存曾测得约 292MB。

| 状态 | 目标总 CPU | 目标内存 | 额外功率估算 |
| --- | ---: | ---: | ---: |
| daemon 空闲，无 LSP | 0～0.5% | 300～450MB | 0.1～0.5W |
| 普通 Graph 查询 | 瞬时 3%～12% | 350～700MB | 查询期间 2～8W |
| MCP + 一个轻型 LSP | 平均 2%～10% | 0.8～1.8GB | 平均 1～5W |
| MCP + 一个重型 LSP | 平均 3%～15% | 1.5～3GB | 平均 2～8W |
| 少量文件增量索引 | 瞬时 10%～35% | 0.8～2GB | 1～5 秒内 8～20W |
| 全量索引 | 30%～70% | 1.5～4GB | 几十秒至数分钟内 15～30W |
| 多 Agent 并发上限 | 由 profile 限制 | balanced 不超过约 3～4GB | 不允许长期跑满 CPU |

### 6.1 增量索引与全量索引

- 增量索引只重新解析新增、修改、删除的文件并修复受影响关系；由 watcher、`sync` 或编辑落盘触发，普通修改通常持续不足数秒；
- 全量索引扫描整个项目，只应在首次 `init`、显式 `index`、提取版本变化、索引损坏或必须完整重建时发生；
- battery 模式可以推迟非必要的全量重建，但索引不兼容时必须返回明确状态，不能继续提供看似正常的旧结果；
- 大规模分支切换、生成代码或全仓格式化可能让增量同步接近全量成本，应合并事件并在阈值后选择更便宜的重建路径。

### 6.2 LSP 与诊断

- CodeGraph 不持续轮询 diagnostics；只在 LSP 查询触及文件时发送 `didOpen`/`didChange`，并在请求 diagnostics 时拉取或等待推送；
- 持续耗电主要来自语言服务器自己的工作区分析、频繁查询和长时间保活；
- 低功率长期运行可能比高功率短时索引消耗更多电量；
- 频繁关闭并重启两个交替使用的 LSP 可能比短暂同时保留更耗电，因此 battery 使用软目标和 LRU，而不是机械的一进一出。

### 6.3 续航目标

以 60Wh 电池、未运行 CodeGraph 时续航 6 小时作为说明性模型：

- daemon 空闲：目标仍约 5 小时 50 分以上；
- battery 模式普通 AI 编程：目标约 5 小时 10 分～5 小时 45 分；
- 一次 5 分钟全量索引：预计减少约 8～15 分钟等效续航；
- 重型 LSP 持续工作时可能降至约 4 小时左右，但空闲回收后不应继续维持该功耗。

能耗不作为普通 CI 的硬断言，因为操作系统调度、温度、供电模式和硬件差异过大。CI 约束 CPU 时间、峰值内存、worker/LSP 数量和任务持续时间；实际瓦数与续航使用固定机器手动记录。

## 8. 主要风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 解释信息过多 | token、延迟增加 | 只解释关键路径；证据、候选和字符数设预算 |
| 动态边误连 | AI 得到错误结论 | precision gate、provenance、反例和真实仓库抽样 |
| 查询池缩容竞态 | 丢请求或关闭活跃 worker | 仅回收 idle worker，状态机和并发测试 |
| 多项目全局 lease 失效 | LSP 超预算或误杀 | PID 身份、心跳、过期清理、活跃请求保护 |
| LSP 切换抖动 | 更慢、更耗电 | 软目标、短时双保留、LRU 和冷启动统计 |
| 双索引占用过高 | CPU、磁盘翻倍 | 默认局部语义差异，深度比较显式且临时 |
| 文件事务不完全 | 残留部分修改 | 同卷暂存、恢复清单、逐文件状态、启动恢复 |
| 输出契约破坏旧客户端 | MCP/CLI 回归 | schema version、兼容字段、契约测试 |
| 大文件继续膨胀 | 维护成本增加 | 新逻辑进入独立 Graph/resource/edit 模块，入口只编排 |
| 自动电池检测不可靠 | 错误限速 | 第一版显式 profile，自动检测后置且可覆盖 |

## 9. 提交与发布顺序

每个阶段使用独立短期分支，从 `personal` 创建并合回；提交保持可单独构建和回退。建议提交粒度：

1. 指标和状态契约；
2. 查询池缩容与 profile；
3. LSP 局部/全局资源预算；
4. 证据模型与现有关系适配；
5. 实现者自动展开与输出预算；
6. 每一种动态分派形状单独提交；
7. Git 改动上下文与局部语义差异；
8. 编辑 operation ID、暂存提交、恢复流程分别提交；
9. 跨平台、评测、打包和文档收尾。

在完成验证前不修改版本号、不发布、不把计划分数写成项目现状。涉及数据库字段时先提供迁移和回退方案，在索引副本上验证；可重建索引不能替代用户配置与编辑恢复数据的备份策略。

## 10. 总体验收条件

本计划全部完成需要同时满足：

- `codegraph_explore` 不依赖新增工具选择即可给出证据、实现者、断链和必要的改动上下文；
- 选定高价值动态流在真实仓库中端到端连接，并降低 AI 的 Read/Grep 回退；
- `codegraph_edit` 对重复请求、部分写入、进程终止和恢复给出确定结果；
- 多窗口和子 Agent 并发后，查询 worker 能自动缩容；
- 同项目共享 daemon/LSP，不同项目受全局 profile 约束；
- battery 模式空闲 CPU 接近零，不后台执行全量分析，普通使用续航增量损失目标为 5%～15%；
- build、全量测试、专项测试、跨平台矩阵和个人安装产物验证均有真实记录；
- 个人版重新测量的检索、性能和资源数据达到阶段预算；
- 文档明确区分计划、实现、验证和发布状态。
